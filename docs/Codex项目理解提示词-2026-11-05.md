## 0. 你的角色与工作方式

你是本项目的接手工程师。先读代码与文档再动手；改动要小、可回退、有定向验证。遵守以下硬约束：

1. **本地全量回归必须先取得用户明确同意。** 普通"继续开发/修复/提交/发布"不包含许可。禁止用裸 `pytest`、拆分运行全部测试、包装脚本或改 CI 环境变量绕过。纯文档、样式、页面小改只做定向检查。
2. **不要主动产生付费模型调用。** 供应商请求必须先记账；失败或不确定的调用不自动重发。没有用户明确授权，不跑真实问答、索引、解析或连接测试。
3. **不要提交或输出密钥、业务原件、数据库、原始模型响应、私有截图。** `.env` 只读不改；不要打印内容。
4. **不要擅自升级数据库结构。** 已有旧库升级须先备份、演练，并显式使用 `-AllowDatabaseUpgrade`。
5. **不要用假数据填充页面。** 后端没有的指标就不画；空态显示真实空态。
6. **前端是无构建的原生 ES Modules。** 不要引入 React/Vue/打包器；中文文案保持一致；不要用 `innerHTML` 拼接业务文本。
7. **服务是三个独立进程 + 一个外部 Docling 服务。** 改前端静态资源后需要重启 web（静态资源带运行指纹），不要只刷新浏览器就断言生效。

## 1. 项目目标与边界

DocQA 是面向**本地与团队试用**的文档工作台：上传资料 → 版本化解析 → 分块/索引 → 知识库授权 → 基于原文的问答与引用 → 摘要与信息提取，并保留任务、结果、来源和质量边界。

核心产品原则：

- **只有文档相关请求才查知识库**；普通闲聊/通用问题直接由 LLM 回答，不返回"知识不足"。
- 已选资料表示"本轮允许读取的集合"，不表示每条消息都必须检索。
- 回答要有逐条事实引用；引用存在不等于问题已被完整覆盖。
- 解析、索引、问答都有已知质量边界；工程通过 ≠ 语义正确 ≠ 持续在线。

明确不在当前范围：多租户 SaaS 化、前端框架重写、真实业务 MCP 接入（N05 未开始）、模型自动改写/自动重发、无授权的全量语义评估。

## 2. 技术栈与运行架构

| 层 | 选型 |
| --- | --- |
| 语言/运行时 | Python 3.11+，Windows 本地部署（PowerShell 启动脚本） |
| Web 框架 | FastAPI + Uvicorn，Pydantic v2 |
| 数据库 | SQLite（单文件 `data/docqa.db`），schema **19**，启动时做结构检查与迁移 |
| 模型 | OpenAI SDK 兼容网关（DeepSeek 配置），服务端持有密钥；前端不可覆盖模型/网关/thinking |
| 解析 | TXT/Markdown 本地解析；PDF/DOCX/XLSX 走独立 Docling/RapidOCR HTTP 服务；`httpx` 显式禁代理和重定向 |
| 向量 | `app/embedding.py` 调 embedding 网关；SQLite 存向量与索引元数据 |
| 前端 | 原生 HTML + CSS + ES Modules，SSE 流式；无构建步骤 |
| 测试 | `tests/*.py`（pytest，150 个文件）+ `tests/web/*.mjs`（Node 合成 DOM/协议测试，16 个） |
| CI | `.github/workflows/rag-quality.yml`，离线分级检查；不使用真实模型密钥 |

运行角色（`scripts/start_local.ps1` 启动，共用同一数据目录）：

- `web`：FastAPI，默认 `127.0.0.1:8000`
- `parse-worker`：`python -m app.parse_worker`，领取解析任务
- `analysis-worker`：`python -m app.analysis_worker`，领取问答/分析任务
- Docling 解析服务：独立 Docker，不由启动脚本管理

运行状态写入 `data/.local-service/{role}.json` 与 heartbeat；`scripts/status_local.ps1 -AsJson` 返回 `ready` / `code_match`。代码或静态资源变更后 `code_match` 会变 false，必须重启对应角色。

## 4. 主要数据流与依赖

### 4.1 上传 → 解析 → 索引 → 发布

1. 上传接口保存原件到 `data/uploads/`，登记 `document_storage_owners` 与容量预留；返回 document + 存储信息。
2. 提交解析创建 `parse_tasks`（202）；`parse-worker` 领取，写 `parse_attempts`。
3. TXT/Markdown 本地解析；PDF/DOCX/XLSX 调 Docling；结果落 `parse_versions`、`blocks`、`sources`、`quality_warnings`。
4. 分块写 `chunks`；索引写 `embedding_vectors_v2` / `embedding_indexes`，固定目标 `parse_version_id`。
5. 知识库发布生成快照（`active_snapshot_id`、`revision`）；授权关系决定客户可见范围。
6. 旧解析/索引/引用不自动改写；新分块只作用于新版本。

### 4.2 提问 → 回答

1. `/app` 提交 `POST /api/chat/conversations/{id}/turns`（202）或新建会话；统一层判断普通对话 / 知识库任务。
2. `analysis-worker` 领取任务；意图路由决定：纯交互、知识检索、工具、澄清。
3. 文档任务：检索规划 → 可选有界补查 Agent（最多一次）→ 证据装入（字符预算 + 上下文额度预留）。
4. 调模型前先 `call_accounting` 记账；回答 JSON 经事实/引用校验后落 `question_results`。
5. 前端通过 SSE `/api/kb-tasks/{id}/events` 或 `/api/question-jobs/{id}/events` 接收 `update`/`state` 事件；断线可带 `after` 游标续传。
6. 引用、反馈、导出都绑定具体结果与版本；反馈可生成回归包与复验证据。

### 4.3 认证与权限

- HttpOnly Cookie 保存会话，页面仅持 CSRF token；变更请求由 `auth-bridge.js` 自动加 `X-CSRF-Token`。
- `team_mode` 由 `DOCQA_TEAM_MODE=1` 控制；开启后管理端/知识库按角色与成员授权过滤。
- 客户只能看获授权且已发布的资料；临时库为个人私有。

### 4.4 前端资源与缓存

- 页面路由由 `main.py` 的 `workspace_page()` 注入 `data-workspace-view` 与静态资源版本前缀。
- 页面与 API 均 no-store；静态资源按运行指纹目录缓存。改前端后必须重启 web 才能拿到新指纹。

## 10. 术语

- **P1/P2/P3**：普通对话分流 / 统一上下文计量 / 有界检索 Agent。
- **N01–N06**：阶段 07 的工作项编号，不是 S0–S5。
- **code_match**：运行进程源码指纹与当前工作树一致。
- **快照 / active_snapshot_id**：知识库一次发布对应的资料版本集合。
- **事实引用**：回答中逐条可回溯到 `sources` 的引用单元。
- **needs_attention**：存在未确认上游调用，需人工核实，不自动重发。
